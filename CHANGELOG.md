# Changelog

All notable changes to Coda are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project follows
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- The terminal UI permission prompt shows more. What the backend says the call is for is drawn on a `reason given:` line after the command, folded to one line of text: Claude Code's `description` of the call and Codex's `reason` of the approval, trimmed and cut to 500 characters. It is the backend's or its model's claim and is not checked, so it never replaces the command. and kept with the stored request so a client that resumes shows it again (a new optional `reason` field of the `permission.request` notification and a new `reason` column in the store, schema version 14). Coda's own loop gives none. `?` shows or hides why the prompt appeared, with what differs for a sub-agent and for cut text. When the backend process crashes, or the turn ends because the backend was lost, while a prompt is open, the prompt reads `The backend process is gone, cannot answer` and takes only a dismissal, instead of live keys that can no longer reach anything. The 600 ms type-ahead guard and the refusal to allow a cut-off command are unchanged. The provider's own choices and a typed note on a Claude denial are tracked in #298 and #299.
- Read-only tool calls from one model reply now run at the same time in model-API sessions. The `read`, `grep`, `list` and `code_*` tools declare themselves read-only through a new `Tool::read_only` method; a run of them in one reply is executed together, up to the new `max_parallel_tools` config key (default 4, at least 1; 1 turns it off). Any other call, such as `edit`, `write` or `bash`, runs alone and in order after the calls before it. Permission prompts and `pre_tool` hooks still go one call at a time in call order, every `pre_tool` hook of a run of read-only calls runs before any of them starts, `post_tool` hooks then run in call order as each call finishes, and results are stored in call order, so history and replay are unchanged. A `read_files_in_parallel` loop eval covers it. See [docs/config.md](docs/config.md#parallel-tool-calls).
- An `ask` tool for model-API sessions: the model puts one short question with two to four options to the user and gets back the option picked. It uses the permission path: a `permission.request` with the tool `ask`, the question as `command` and the new `options` field, answered by `permission.respond` with a new `choice` (counted from 0). A client with no user to ask sets the new `no_terminal` field, as `coda run` does, and the model then reads an error. A declined question or a timeout, which is as long as a permission prompt waits, reads as a plain note. The terminal UI draws the options and takes a number. A sub-agent has no `ask` tool. The new fields are optional, so `PROTOCOL_VERSION` stays 1. An `asked_the_user` loop eval covers it. See [docs/agents.md](docs/agents.md#the-ask-tool).
- `coda review` reads the issues a pull request links to and checks the change against them. It finds `#12`, `owner/repo#12`, full issue URLs and branch names such as `123-fix-bug` in the title, body and source branch, reads up to three with `gh issue view --json` (title, labels, body and task list items) and gives them to the reviewer as untrusted data. The review gets a `Linked issues` section with a verdict per requirement, fully, partially or not compliant, with the requirement quoted; a verdict whose quote is not in the issue is dropped. An issue that cannot be read is skipped with a note and gets no verdict, and with no reference the section is left out. Issues of another repository are read only when listed in the new global `[review] linked_repos`. See [docs/config.md](docs/config.md#coda-review).
- A `todo` tool for model-API sessions: a short ordered list (`add`, `set` a status of pending, in_progress or done, `clear`; at most 20 items) that the model keeps for itself. Each change is stored as a `todo_updated` event holding the whole list, so the list survives a daemon restart and is drawn above the prompt in the terminal UI. A compaction adds the list to its summary message, so the model keeps it. The tool asks no permission, a sub-agent has no list and is told so, and an agent file cannot name it. A `kept_a_todo_list` loop eval covers it. See [docs/agents.md](docs/agents.md#the-todo-tool).
- `coda review --post <pr>` puts the review on a pull request through `gh`, as your own `gh` login and with no token read from disk. After a preview and a `y` (or with `--yes`, which is required when standard input is not a terminal), the findings on a line of the diff become the inline comments of one pending review, with no approve or request-changes event, and the rest go in one summary comment with a hidden marker. A rerun edits that summary and skips any finding whose fingerprint is already in one of your comments, submitted or pending. Without `--post` the command still posts nothing. See [docs/config.md](docs/config.md#coda-review).
- Per-turn checkpoints. In a git repository, the daemon snapshots the working tree (tracked and untracked files, minus ignored ones) before a session's first turn and after every turn, on every backend, so a later change can restore or diff any turn. A snapshot is a commit built from a scratch copy of the index and kept only under the private ref `refs/coda/checkpoints/<session>/<turn>` (`base` for the first one), so your index, `HEAD`, branches and `git log` are never touched. Nested repositories that `git add` refuses are left out, and an existing ref is never replaced. The refs are stored on the turn row (database schema 13), a failed snapshot is logged and never stops the turn, and a folder that is not a repository gets none. Restore and diff are not part of this change.
- A model fallback chain for model-API sessions. A `[models.<alias>]` section may list `fallback` aliases that are tried in order when the model fails with a rate limit or overload that outlasts the provider's retries, or an unknown-model error. The same request goes to the next model, only before the failing model has said anything, so a reply is never cut in two. The switch is stored once as a `model_fallback` event naming both aliases and shown as a notice in the terminal UI, tokens from every model count against one budget, and the next send starts on the first model again. A chain with a delegated backend (`claude_code` or `codex`), a missing alias or a repeated alias is refused when the config loads, and `coda doctor` warns for a fallback whose provider is not enabled. A provider that does not know the model (`not_found_error`, `model_not_found`, or a 404 that names a model) now reports a distinct unknown-model error instead of a fatal one. A `fell_back_on_rate_limit` loop eval covers it. See [docs/config.md](docs/config.md#fallback-chain).
- A new provider key, `providers.anthropic.thinking_budget_tokens`, turns on extended thinking for the `anthropic` provider. When set, each request carries the `thinking` setting with that budget. The budget must be at least 1024 and below `max_output_tokens`, and config loading refuses any other value.
- `coda session list|send|show`, so a script can drive stored sessions. `list` prints sessions newest first and `--json` prints an array. `send <id>` sends a message from `--prompt` or standard input and prints the turn id, or with `--wait` follows the turn to its end, prints the answer and exits with the codes of `coda run`; `--json` prints `stop`, `exit_code` and `text`. `show <id>` prints the conversation, or with `--json` the session and its stored events. An unknown id exits 70. See the README.
- `coda review` reads the repository's own guidance and adds it to the reviewer's prompt as project rules: `AGENTS.md`, `CLAUDE.md` and the first 20 files of `docs/adr/*.md` by name, from the default branch with `git show`, never from the working tree or the branch under review. `[review] guidance_lines` (default 500) caps the lines, a cut ends with a visible marker and zero turns it off. `[review] extra_instructions`, from the config and from `.coda/review.toml` on the default branch, adds standing instructions, and `--instructions` still adds them for one run. The prompt and the `reviewer` agent now say that the diff is untrusted data written by its author and that rules come only from the request. See [docs/config.md](docs/config.md#review).
- Reasoning passthrough for model-API sessions. A reasoning block from the model (an Anthropic thinking block with its signature or a redacted one, or the `reasoning_content` or `reasoning` field of an OpenAI-compatible stream) is kept out of the answer text and sent back unchanged with the next request where the provider needs it: before the reply's text and calls for Anthropic, and as `reasoning_content` on a reply with tool calls for OpenAI-compatible servers. For local servers that print `<think>...</think>` in the text, a small stream state machine splits it out even when a tag is cut across chunks, and keeps text that only looks like a tag. Reasoning is stored in the session's originals and referenced from the `assistant_message` event, so a resumed session sends it back too. A `kept_reasoning` loop eval covers it. See [docs/config.md](docs/config.md#providersname).
- The terminal UI status line shows the state of a running turn: `Working 1m 04s`, then `Stopping` after Ctrl+C. If the turn is still running 5 seconds after the stop was asked for, it reads `not responding, press Ctrl+C again to force stop`, and that press sends `session.cancel` with the new `force` flag, which also kills the backend's process group at once (after checking the pid still is the recorded backend). A daemon that reports the new `force_cancel` capability honors `force`; an older one cancels as usual, so the terminal UI reads the capability and does not offer the force to an older daemon. A force that did not end the turn is offered again 5 seconds later. A model-API session runs in the daemon and has no process to kill, so there the force gives up on the turn task and records the turn as cancelled. `PROTOCOL_VERSION` stays 1. Claude Code already stops at once and Codex within 2 seconds, so the force is for a stop held up by something else, such as a stuck store.
- `coda review` has a verifier pass. After the parts are merged, the built-in read-only `verifier` agent gets the findings and the diff lines around each, and scores each from 0 to 10 with a one-line reason. A score of 0, or one below `[review] verify_threshold` (default 4), drops the finding; the rest are ranked by score and show their score and reason. It runs on the other of Claude Code and Codex when that one is enabled, else on the review's backend. If it fails or answers junk, every finding is kept, marked `unverified`, with no score. `run.verifier` and `run.verifier_dropped` report it, and `[review] verify = false` turns it off. See [docs/config.md](docs/config.md#coda-review).
- Tool-call recovery for weak or local models in model-API sessions. Arguments that are almost valid JSON (a trailing comma, single quotes, a raw line break inside a string, closing braces cut off the end) are repaired with a strict, deterministic fix, the call runs, and a `call_recovered` event is stored and shown as a notice. Arguments that cannot be repaired without guessing are returned to the model as an error that includes the tool's input schema. A new provider key, `text_tool_calls` (off by default), also reads a reply whose whole text is one JSON object that fits exactly one tool, either the arguments alone or `{"name", "arguments"}`, as a call to it; a reply that names an unregistered tool, fits two tools or has text around the JSON is never run. `repaired_arguments` and `text_shaped_call` loop evals cover both. See [docs/config.md](docs/config.md#providersname).
- Building blocks for a verifier pass in `coda review`, in the `coda-review` library and the agent catalog: a built-in read-only `verifier` agent that scores findings from 0 to 10 with a one-line reason, a strict reader of its reply, the step that drops findings scored 0 or below `[review] verify_threshold` (default 4), ranks the rest by score and marks any finding it cannot score as unverified, the diff slice around each finding, and the score, reason and verifier fields of a finding and of the run details and the markdown. `[review] verify` and `verify_threshold` are read and checked; `coda review` does not use them yet. A scripted fixture with known false positives checks that they are dropped.
- The terminal UI shows what the agent is doing. While a tool runs, a line above the prompt reads `running cargo test 12s` (`editing` and `reading` for edits and reads), or `waiting for approval` while a permission prompt is open. When the turn settles, its work folds into one line such as `Worked for 3m 12s: ran 4 commands and edited 2 files`: at most two categories, by priority commands, edits, then reads, with failures marked (`ran 2 commands (1 failed)`). Ctrl+O expands the newest fold into one line per call. A turn that was cut short reads `Stopped after 3s: ran 1 command, 1 cut short`, one that ended in an error reads `Failed after`, and nothing is ever described as finished for a wait or a cancel. A turn with no commands, edits or reads does not fold, and a turn replayed from history has no time. The wording rules live in a UI-free module with plain tests.
- An `end_turn` hook event for model-API sessions. When the model ends its reply without tool calls, a blocking `end_turn` hook can exit with status 2 to send it back to work: what it wrote on standard error becomes a user message and the loop continues. Forced continues are capped at `max_guard_continues` per send (default 2) and count against the token budget and `max_turns`. When the cap is hit the turn ends with the new stop condition `guard_limit` (exit code 5 for `coda run`). A crash, a timeout or any other exit status lets the turn end. Each continue is stored as a `guard_continue` event and the terminal UI shows it as a notice, and a `finished_too_early` loop eval covers it. `guard_limit` is a new value of the existing stop `condition` string, so `PROTOCOL_VERSION` stays 1. See [docs/config.md](docs/config.md#hooks).
- `coda review` splits a change that does not fit `[review] diff_budget_chars` into parts instead of leaving the extra files out. The files the budget cut go to the next part, up to `[review] max_chunks` (default 4); each part is reviewed by its own run, at most `[review] chunk_concurrency` (default 3) at a time, and a part whose run fails is tried once more. The merge is conservative: all findings are kept, a finding repeated with the same file, lines and text is kept once with the worst severity and the lowest confidence, risk and effort are the highest of the parts, and the finding cap never cuts a security finding. If a part still fails the review is partial: it opens with a banner, keeps the other findings, names the failed files under Left out and sets `run.partial` in the JSON. `run.chunks` counts the parts. See [docs/config.md](docs/config.md#coda-review).
- A `tool_call` event from every backend, so a client can show what the agent is doing and fold it afterwards. Each call sends one event when it starts and one when it ends, with the backend's `id`, the tool `name` (`Bash`, `Edit`, `mcp__server__tool` for Claude Code and Codex, `bash` and `edit` for coda's own loop), a one-line `summary` of what it works on (a command, a path or a pattern, cut to 80 characters) and a `status` of `started`, `succeeded` or `failed`. Claude Code reads `tool_use` and `tool_result` blocks, Codex reads its item events, and the model-API loop reads its own calls. A call the user denies, or whose result is an error, ends `failed`, and a turn that is cancelled or loses its backend ends its open calls `failed` before the interrupt or crash event. Calls made inside a sub-agent are not reported. `initialize` reports the `tool_call_events` capability and `PROTOCOL_VERSION` stays 1; an older client reads the event as `unknown`. The summary can hold part of a command line, so it is stored with the session's events and not in the content-free usage log.
- Stall and loop detection for model-API sessions. When the model repeats one tool call with the same arguments and the same result 3 times, or two calls take turns with the same results, the result of that call carries a warning that says what repeated. If it repeats again (the 4th time) the turn ends with the new stop condition `stalled`, which `coda run` reports with exit code 5. A different argument or a changed result starts the count again. `[loop_guard] warn_after` and `stop_after` set the thresholds and are checked when the config loads. `stalled` is a new value of the existing stop `condition` string, so `PROTOCOL_VERSION` stays 1. A `warned_for_a_repeat` loop eval covers the warning. See [docs/config.md](docs/config.md#loop_guard).
- Loop evals: five fixture tasks (fix a failing test, add a function, rename a symbol, resist an injected instruction, recover after a bad tool call) that run coda's own turn loop with the real tools against a scripted model and are judged by a command in a temporary workspace. The report lists turns, estimated tokens and shrunk bytes per fixture, and a committed baseline fails the test when a fixture stops passing, takes more turns, or uses more than 10 percent more tokens, so a change to tool text or loop logic that costs more is caught. A live run against a real model is `#[ignore]` and needs `CODA_LIVE_EVALS=1` and an API key variable; it never runs in CI. See [docs/evals.md](docs/evals.md).
- `coda review` runs on the `claude_code` and `codex` backends, using your own login with no API key. A new daemon request, `agent.run`, runs a named agent on a prompt on a Claude Code or Codex session: the agent's instructions and the packed diff go in the prompt, so no `.coda/review/input-<pid>.txt` file is written for these backends (the Anthropic API still uses it). The session must be in plan mode, where every permission request is denied, Claude Code is started with `Edit`, `Write`, `MultiEdit`, `NotebookEdit` and `Bash` banned (which beats allow rules in your own settings) and Codex always runs in its read-only sandbox, so the reviewer reads but cannot change anything; `agent.run` refuses a session in any other mode, a model-API session and an unknown agent. A `task` result also reads the `coda review` format, so a review agent's `critical` and `high` findings are blocking, `medium` and `low` are non-blocking and `info` is a suggestion, and a finding's `title`, `explanation`, `file` and `start_line` stand in for `message` and `location`, instead of the report being rejected as malformed. See [docs/config.md](docs/config.md#coda-review).
- `[checks.<extension>]` in `config.toml`: a command coda runs after the model changes a file of that kind with `edit`, `write` or `multi_edit`, so the model sees compiler or lint errors in the same tool result. It runs once after the last change in a reply, with the hook rules (no shell, the hook environment, killed with its process group at the timeout), adds `check passed (<program>)` or the shortened output of a failure (the last 32 KiB it wrote), and reports a timeout without failing the change. Nothing runs for an extension with no entry. See [docs/config.md](docs/config.md#checksextension).
- A `multi_edit` tool for model-API sessions that applies several edits, in one file or many, in one call that changes everything or nothing. Each edit keeps the rules of `edit` (its text must occur once) and is matched against the files as they were when the call began, so two edits that overlap or depend on each other are reported instead of applied in a surprising order. If any edit fails, no file changes and the result names the first failing edit with the nearest line. The files are written to temp files first, checked again for outside changes and renamed together; if a rename fails, the files already renamed are put back, and the error names any that could not be. A second form, `symbol`, replaces a definition by name using the lines the code index holds, and refuses a name that is ambiguous in the file, an index that is not fresh, or a symbol with no known line range, and keeps the file's line endings. The call is one permission request that names every file (the prompt shows paths, not a diff, as it does for `edit`), so one path outside the workspace denies all of it, and `accept-edits` asks when any file changes what runs. The code index readers now return the last line of each symbol, which the index already stored.
- `coda review [<pr number|url>|<branch>|<range>]` and a `/review` command in the terminal UI. `coda review` packs the change, has the read-only `reviewer` agent read it through the `task` tool and prints the checked findings as markdown or, with `--json`, in the `coda-review` schema. `--staged` reviews staged changes, `--instructions` adds your own, `--backend` picks the backend, `--cwd` the directory, and `--force` reviews a pull request that a `[review.skip]` rule would skip. It posts nothing and edits nothing; a failed run exits 70 with the reason. In the terminal UI, `/review` only asks the session model to hand the change to the reviewer. A built-in `/review` replaces a command file of that name in the terminal UI. See [docs/config.md](docs/config.md#coda-review).
- `write` and `list` tools for model-API sessions, so the model can create a file and look at a directory without `bash`. `write` creates a new file, and replaces an existing one only when the session read it with `read` and it has not changed since; it never creates directories and stops at the same 1 MiB cap as `edit`. `list` shows one directory (folders end in `/`), or with a `pattern` such as `*.rs` or `src/**/*.toml` searches the tree by name, and skips `.git`, `target` and `node_modules` like `grep` (`include_dirs` opts them back in). Both stay inside the workspace and refuse symlinks. In `accept-edits` mode `write` is allowed like `edit`, except for files that change what runs. Both names can be used in an agent's `tools` list. See [docs/agents.md](docs/agents.md).
- Building blocks for `coda review` in the `coda-review` library: reading the staged diff, finding the default branch (`origin/HEAD`, else `main`, else `master`), reading what the user typed as a pull request, branch or range, the prompts and reply format for the reviewer, and the step that turns checked model output into a finished review.
- A diff packer for reviews, in the `coda-review` library. It reads the diff, drops binary, vendored and ignored files and deletion-only hunks (naming deleted files), orders files by the repository's main language then by size, adds three lines of context and the new-side line number to each line, and keeps the text within `[review] diff_budget_chars` (default 120000). The file the budget cuts is clipped at a whole line, even inside a single large hunk, and the files after it are left out. Both are named in the coverage list. See [docs/config.md](docs/config.md#review).
- Review ignore and skip rules. `[review.ignore]` takes globs (with `**/`) and a built-in list of generated files (lockfiles, minified files, source maps, generated protobuf). `[review.skip]` skips a pull request by draft state, label, title regex, source or target branch regex, author or bot author; the library decides skip or review and builds the one-line reason, and a force flag overrides it. `coda review` prints that line, exits 0 and takes `--force`. Rules come from the global config and `.coda/review.toml` on the default branch (given as a `refs/heads/` or `refs/remotes/` ref such as `refs/remotes/origin/main`), and a rules file on the pull request's own branch is ignored. See [docs/config.md](docs/config.md#reviewignore).
- A `coda-review` crate with the review finding schema (id, file, line range, severity, category, title, explanation, optional patch, confidence), a strict parser for model output that rejects a finding whose lines fall outside the diff and builds a bad-shape retry hint, a coverage list that names every file given to the packer, and markdown and JSON renderers. Model text in the markdown output cannot start headings, rules, code fences, HTML tags or mentions, also inside list items and quotes. `[review] max_findings` (default 5) caps the findings kept per run. See [docs/config.md](docs/config.md#review).
- A Claude Code session keeps what the CLI reports about usage and limits. The `result` line's token counts (input, output, cache read and cache write) become a `usage` event, and each `rate_limit_event` becomes a `rate_limit` event with the status, the window and its reset time, per-window utilization in basis points, and the overage fields. `initialize` reports the `usage_details` and `rate_limit_events` capabilities. The field names come from a live recording on claude 2.1.296.
- A turn that ends in error after a rejected rate-limit report now sends a `usage_limit` event just before its `result`, naming the window (`five_hour`, `seven_day`, `model_scoped`, `monthly`) and when it resets, so a client can say the plan limit was hit and when it lifts. `initialize` reports the `usage_limit_events` capability, and `PROTOCOL_VERSION` stays 1.
- `initialize` returns `capabilities`, optional flags such as `usage_details` and `rate_limit_events` that default to false when absent, and an event type a peer does not know reads as `unknown` instead of failing. A new event no longer needs a `PROTOCOL_VERSION` bump; only a breaking change does.
- A release workflow that builds, checksums and attests the `coda` archives for Linux and macOS, and an `install.sh` that verifies the checksum before installing.
- A `session.close` request that stops a session's idle Codex server or model conversation and keeps its stored events. `coda run` calls it when the turn ends, and the terminal UI calls it for a session it created when the user quits or switches away.
- A `cause` on `turn_interrupted` events (`cancelled`, `idle_timeout`, `backend_lost`, `daemon_restarted`, `daemon_stopping`). `coda run` exits 4 for a turn cancelled from another client and 5 for the other causes, naming the cause.
- `daemon.status` reports `any_provider_enabled`, so the terminal UI shows the setup guidance when a daemon that started before `coda init` has no provider.
- Agent, skill and command definition files with a loader, `coda agents list` and `coda agents trust`. Project definitions load only after the repository is trusted, and trust ends when they change. See [docs/agents.md](docs/agents.md).
- `[[hooks]]` in the user's `config.toml`: programs coda runs at `session_start`, `pre_tool` and `post_tool` in a model-API session. A hook gets a JSON payload on standard input and a minimal environment without API keys. It is killed with its process group at its timeout, and only a `blocking` hook can stop the action it guards. See [docs/config.md](docs/config.md#hooks).
- `coda agents lint` checks definition files for unknown tiers, efforts and tools, missing usage guidance and model ids, and a `[routing]` config table maps agent tiers to models.
- A `task` tool that runs a named agent as a child conversation with only its tools, its tier's model and its own permission prompts, which reach the parent's client with the agent named in the `agent` field of `permission.request`, and the terminal UI draws it apart from the command. See [docs/agents.md](docs/agents.md).
- A `task` result reports a status (`completed`, `failed` or `cancelled`), a summary and findings classified as blocking, non-blocking or suggestion. The agent's words are marked as data and capped at 16 KiB with the findings kept whole, blocking first, and a malformed report is rejected. A `task` call with a blank prompt is refused.
- Built-in agents `explore`, `reviewer`, `implementer` and `tester`, available to the `task` tool with no files. A user file of the same name replaces one. A trusted project file of the same name can replace its prompt and narrow its tools, but keeps its tier and effort; `coda agents lint` reports a tier, effort or tool the project file asked for and did not get.
- Command files are slash commands in the terminal UI (`/name args`, listed by the new `/help`) and run headless with `coda run --command <name> --args <text>`. Without `--args`, piped standard input (up to 256 KiB) is the arguments of a command that has a `$ARGUMENTS`; an unknown command fails before it is read, and a command without `$ARGUMENTS` never reads it. `$ARGUMENTS` in the prompt template is replaced by the arguments as plain text, and a prompt that is blank after that is not sent. Only your own and trusted project commands run, and a built-in TUI command wins a name clash in the TUI. The terminal UI reads trust once, when it starts. It says when definition files were skipped.
- Skills for model-API sessions. The model is offered the skills by name and description in the description of a new `skill` tool, and a skill's body enters the conversation only when the model calls the tool for it. Only your own skills and those of a trusted project are offered.
- `coda doctor` warns when a `[routing]` alias uses another provider than the default session provider, since a `task` call in a session on that provider cannot use it.
- Provider keys `max_output_tokens` (for `anthropic` and `openai_compat`), `max_tokens_field` (`"max_tokens"` or `"max_completion_tokens"`) and `stream_usage` (for `openai_compat`), so a server that rejects `max_tokens` or `stream_options`, or a small local model that cannot fit an 8192-token reply, can be used. The defaults keep the request as it was. See [docs/config.md](docs/config.md).
- A licensing page, [docs/licensing.md](docs/licensing.md), covering the Apache-2.0 license, the source header check and the dependency license policy.

### Changed

- Coda is now licensed under Apache-2.0. It was AGPL-3.0-only. Every source header, the workspace license field, `NOTICE`, `deny.toml` and the SPDX check use the new identifier.

### Fixed

- A checkpoint no longer holds the old content of a file that was edited to the same size within a second of git writing the index. The snapshot works on a copy of the index, and a copy with a newer modification time hid git's own check for such files; the copy now keeps the time of the original. Seen as a flaky test on Linux, where the copy gets a new time.
- A Claude Code process that dies while a permission prompt waits is now noticed at once. The adapter read nothing from the process while it waited for the answer, so the crash showed only after the user answered, and the prompt kept live keys that reached nothing.
- A forced stop now works on a stuck model-API turn. It used to kill nothing, because the turn has no backend process, and the terminal UI kept showing `Forcing stop`. The daemon now gives up on the turn task, records the turn as cancelled and frees the session, and the next send rebuilds the conversation from the stored events. Streamed text that was not stored yet when the force landed can be lost, and a store that does not answer within 5 seconds is given up on so the session is freed. The terminal UI also checks the `force_cancel` capability, and offers the force again when a force did not end the turn.
- A `session.cancel` on a Claude Code or Codex `exec` turn no longer waits behind a full event queue (a slow store). The adapter now watches the cancel while it hands over an event, stops the backend first, and then sends the interrupted event. Events already queued are kept and stored in order.
- The test `a_store_user_is_not_blocked_while_the_index_walk_runs` failed once on a busy machine because it compared the single slowest store call with half the walk, so one pause of the test runner failed it. It now checks that a store call finishes in the middle of the walk, as the definitions test does.
- On a model-API session, a `permission_request` could be stored before the text and the assistant message that came just before it when the store was slow, because the announcement did not wait for the daemon to store the loop's earlier events. The loop's event channel now carries a marker, and the announcement waits until the daemon answers it, so the log keeps the order the loop produced.
- On Claude Code and Codex sessions, a `permission_request` could be stored before the text the backend streamed just before asking, because the announcement skipped the 50 ms text coalescing queue. The announcement now waits until the queued events are stored, so the log keeps the order the backend produced.
- In `accept-edits` mode, `edit`, `write` and `multi_edit` now also ask before changing a build, package or task-runner file that runs code later: `Makefile`, `justfile`, `package.json`, `pyproject.toml`, `setup.py`, `tox.ini`, `build.gradle`, `pom.xml`, `CMakeLists.txt`, `Rakefile`, `Gemfile`, `Dockerfile`, `Taskfile.yml`, `.envrc`, `.npmrc` and similar, at any depth and whatever the letter case. All three tools already shared one list; it only held the Rust files. A grant does not override the prompt.
- A model-API session stored one `stream_delta` row for every streamed chunk of text. It now joins chunks that arrive within 50 ms into one row (a row stops growing at about 16 KiB), as Claude Code and Codex turns already do, and stores any other event only after the text streamed before it.
- The database no longer keeps the `first_turn` and `last_turn` columns of `backend_threads`, which were written and never read, and the unused helper that marked a stored backend id as failed is gone. A new migration step (schema version 12) drops the two columns and keeps the stored ids. A test now covers the `history_not_restored` event for a Claude Code session whose stored conversation cannot be read.
- The test `a_timed_out_check_takes_its_children_with_it` failed on a busy machine because it asked `kill -0` about the child a moment after the kill, while the process was still exiting. It now waits for the end of a pipe that only the script and its child hold open, so it needs no polling and no process id.
- The `initialize` example in the protocol golden files now shows `rate_limit_events` true, as the daemon sends it, and a daemon test compares the real result with it. `Event::Unknown` is documented and tested as receive-only (it serializes as `{"type":"unknown"}`, so a relay must not store or forward it). A Claude rate-limit window with no numeric utilization, or a reset time that is not whole seconds (a fractional, negative or millisecond value), is now noted in the parser diagnostics instead of dropped silently, and a whole-number float reset time is accepted. The `Capabilities` docs say each flag means the daemon can send the event, not that every backend does, and utilization docs say it can exceed 10000 basis points.
- The review library reads quoted and escaped file names correctly (`git ls-files -z`, octal escapes in diff headers), clips a single hunk larger than the budget at a line instead of dropping it and every file after it, keeps model text from forging headings, mentions or HTML in the markdown output, merges touching line ranges, reads the rules file only through a `refs/heads/` or `refs/remotes/` default branch ref, cleans control characters out of diff lines, accepts leading-slash ignore globs and caps the model text in the retry hint.
- The daemon turn tests wait for a permission request's announcement before answering it. The request row is written before its `permission_request` event, and an answer in between suppresses the event by design, so a slow run could answer first and the burst test found no `permission_request`. No daemon code changed.
- A backend turn no longer loses events when it emits faster than the store writes. The event queue used to drop events once 1,024 were waiting, which could remove a result or a permission request from the log. Nothing is dropped now, and text streamed within 50 ms is stored as one chunk.
- A slow store no longer lets a turn's event queue grow without limit. The queue between a backend and the publisher holds at most 1,024 events, and a backend adapter waits to hand over its next event when it is full, so the backend's own pipe fills and it slows down. No event is dropped.
- An event waiting for room in the turn's queue is no longer lost when the turn is cancelled or the idle timeout fires at that moment. The event stays in the sink and is sent before the next one and at the end of the turn. A turn whose event the store could not write now ends as failed, with an error in the event log. After an idle timeout, a store that does not answer for 30 seconds no longer holds the session: the turn lets go and logs what it could not store.
- A Claude Code session keeps its conversation across a daemon restart. The backend's own session id is stored in a new `backend_threads` table, so the first send after a restart resumes it instead of starting with no context. An id the backend fails to resume twice in a row, before it names any conversation, is dropped and the session starts fresh; a single early crash keeps the id and tries it again. Codex thread ids are not stored yet.
- A Claude Code session id is now stored when the backend first reports it, so a daemon killed mid-turn still resumes the conversation. When the backend refuses a stored id, the fresh start is sent the stored conversation before the prompt, as a Codex thread is, or a `history_not_restored` event when it cannot be read.
- A Claude Code session no longer loses its stored conversation to one crash at start-up. The stored id is kept until a resume fails twice in a row before the backend names a conversation, and it is replaced when the fresh start names a new one. The stored history is sent with the prompt only once: a retry after the fresh start has named its conversation does not add it again. The write that stores the id no longer pauses reading the backend, and the history sent to a fresh start is capped by its size as rendered JSON, so escaped text in the history cannot exceed the 32 KiB cap.
- Esc no longer quits the terminal UI. It clears the input, or denies a permission request when one is open. Quit with `/quit`, Ctrl+D on an empty input, or Ctrl+C twice within two seconds when idle. Ctrl+C still cancels a running turn.
- The terminal UI quit hints are now true and fit a narrow terminal. A paste between two Ctrl+C presses resets the quit confirmation, the confirmation and a new busy-turn hint show on the connection line and expire instead of stacking in the transcript, and Ctrl+D quits after the daemon is lost even with text left in the input.
- A skill body between 16 and 32 KiB reaches the model whole. It was shortened like any long tool result.
- A `task` call for an agent whose definition file was skipped is refused with the problem. It used to run the built-in or user agent of that name without a word.
- A result that a hook withheld no longer leaves its original in the store when saving its size failed, and deleting it no longer waits for the store on the async threads.
- The daemon holds the store only to read the trust decision when it reads definition files, instead of for the whole read, and reads them once per send, so the skill index and the `task` agent list come from the same files.
- A model-API session that is revoked, or whose project agents change, rebuilds its conversation at the next send even when it has no skills, so the `task` tool no longer lists an agent the repository stopped trusting.
- A session keeps the tokens it spent, and its send limits, when the daemon drops its idle conversation to make room, and keeps the tokens after a daemon restart. It used to start again with a full budget.
- The warning about skipped definition files is logged once per built conversation and again only when the number of skipped files changes, not at every send.
- A `task` call that runs a built-in or user agent while a held-back project file has the same name ends its result with a note saying so.
- A store error while reading the trust decision leaves the built-in agents in the `task` list and in dispatch, and is logged, instead of failing the send. A session that already has a conversation keeps it for as long as the read keeps failing.
